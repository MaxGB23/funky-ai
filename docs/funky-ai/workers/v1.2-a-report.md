# Return Envelope: Auditoría CI/CD Gentle AI

## Resumen de la Auditoría
He inspeccionado el directorio `docs/gentle-ai/.github/workflows/`. Gentle AI cuenta con 3 flujos principales:
1. `ci.yml`: Validación básica de PRs y pushes a `main`. Ejecuta Unit Tests y E2E tests con Docker.
2. `pr-check.yml`: Un flujo estricto de gobernanza de Pull Requests. Verifica que exista un Issue vinculado, que dicho Issue tenga la etiqueta `status:approved`, y que el PR tenga exactamente un label `type:*`.
3. `release.yml`: Automatización de releases en pushes de tags (`v*`) usando GoReleaser.

## Políticas de QA Transferibles (Ecosistema Node.js)
Las siguientes prácticas son directamente adaptables a nuestro futuro `funky-cli` en Node:

- **Estructura de CI en PRs y Main:** Ejecutar tests en PR y push a main es estándar. Podemos adaptar esto usando `actions/setup-node` (con soporte built-in para caché de `pnpm`, según nuestra convención global).
- **Semántica de PRs (Labels):** Exigir exactamente un label de tipo (`type:bug`, `type:feature`, `type:refactor`, etc.) en cada PR. Esto sentará las bases para automatizar la generación de changelogs.
- **Validación Estricta de Issues:** La obligación de vincular un Issue (`Closes #123`) en la descripción del PR para asegurar trazabilidad previene que se introduzca código no planificado en el Backlog.
- **Automatización de Releases:** Reemplazar GoReleaser por herramientas del ecosistema Node (como `semantic-release` o `release-it`) para publicar automáticamente en npm o subir binarios cuando se mergea a main o se taguea una release.

## Over-engineering (Antipatrones a Evitar)
- **Bloqueo por API para el `status:approved`:** El workflow `pr-check.yml` hace un script complejo pegándole a la API de GitHub para verificar que el Issue vinculado tenga el label `status:approved`. Para Funky AI en su estado inicial, esto ralentizará el iterado. Podemos exigir el Issue vinculado, pero no bloquear por etiquetas específicas de aprobación hasta iteraciones más maduras o equipos más grandes.
- **Complejidad del script E2E:** En Gentle AI ejecutan contenedores Docker adicionales y scripts para E2E testing directo en la CI en cada push. Dado que `funky-cli` lidia con archivos de disco, inicialmente sugerimos mockear el file system (ej: `memfs`) para tests rápidos antes de lidiar con ambientes E2E costosos.

3. **Draft Release Pipeline:** Considerar la configuración de generadores de binarios como `pkg` o `esbuild` si pretendemos publicar un CLI portable, y documentarlo en la propuesta arquitectura.
