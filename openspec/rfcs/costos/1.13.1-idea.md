# Nueva Capa de Constraints Arquitectónicos y Refactor del Flujo `funky assess`

## Contexto

Durante la implementación y uso inicial de `funky assess`, identificamos una limitación importante en el flujo arquitectónico actual.

El sistema funciona bien como una primera capa de linting arquitectónico, pero todavía asume implícitamente que:

```txt
si las reglas heurísticas locales pasan → probablemente la arquitectura está bien
```

Y esa suposición es incorrecta.

En proyectos reales, las malas decisiones arquitectónicas rara vez nacen de contradicciones técnicas obvias. Normalmente aparecen por restricciones operacionales, de negocio, compliance, mantenimiento u organización que nunca fueron capturadas explícitamente.

Ejemplos:

* Equipo junior + complejidad de Kubernetes
* Datos gubernamentales + ambigüedad regional en serverless
* Bajo presupuesto + expectativas de alta redundancia
* Solo maintainer + arquitectura de microservicios
* MVP pequeño + sobreingeniería prematura

Actualmente los templates (`PROJECT-CANVAS`, `INFRA-CANVAS` y `architecture-assessment.md`) siguen estando demasiado orientados a:

* descripción del producto,
* definición del stack,
* y setup técnico.

Pero todavía capturan poco sobre:

* realidad operacional,
* riesgo de negocio,
* ownership de mantenimiento,
* tolerancia a fallos,
* prioridades arquitectónicas,
* y constraints reales del sistema.

Como consecuencia, el Orquestador IA recibe contexto incompleto.

Y considerando que:

```txt
Garbage In → Garbage Out
```

la calidad del razonamiento arquitectónico queda limitada.

---

# Insight Principal

El problema NO es simplemente:

```txt
“necesitamos más campos”
```

El verdadero problema es:

```txt
“no estamos extrayendo explícitamente los constraints arquitectónicos”
```

Agregar decenas de campos a un único template monolítico probablemente:

* aumentaría la carga cognitiva,
* empeoraría la UX,
* intimidaría a developers junior,
* y volvería innecesariamente pesado el onboarding para proyectos pequeños.

En lugar de eso, deberíamos evolucionar hacia:

```txt
un pipeline progresivo de descubrimiento arquitectónico
```

---

# Dirección Propuesta

## Mantener Inicialización Ligera

El flujo actual tiene una ventaja fuerte:
el onboarding sigue siendo rápido y accesible.

Actualmente:

* `PROJECT-CANVAS` → intención del producto
* `INFRA-CANVAS` → stack técnico

Y eso debería mantenerse relativamente pequeño y amigable.

Especialmente para:

* MVPs
* freelancers
* startups
* pequeños negocios
* developers junior

No deberíamos convertir la inicialización en burocracia enterprise.

---

# Introducir una Capa Dedicada de Constraints

En vez de expandir indefinidamente `architecture-assessment.md`, introducir un nuevo documento especializado:

```txt
ARCHITECTURE-CONSTRAINTS.md
```

Este archivo se generaría o requeriría durante:

```bash
funky assess
```

Y tendría una responsabilidad clara:
extraer restricciones y realidades arquitectónicas críticas.

---

# Separación Arquitectónica de Responsabilidades

## PROJECT-CANVAS

Responde:

```txt
¿Qué estamos construyendo?
```

Contiene:

* idea del producto
* funcionalidades
* usuarios
* alcance
* intención de negocio

---

## INFRA-CANVAS

Responde:

```txt
¿Con qué stack lo vamos a construir?
```

Contiene:

* frontend/backend
* base de datos
* hosting
* despliegue
* overview de infraestructura

---

## ARCHITECTURE-CONSTRAINTS

Responde:

```txt
¿Qué realidades y riesgos pueden romper este sistema?
```

Contiene:

* compliance
* ownership operacional
* expectativas de SLA
* impacto de fallos
* concurrencia esperada
* restricciones de presupuesto
* seniority del equipo
* disaster recovery
* auditabilidad
* complejidad de integraciones
* expectativas de escalabilidad
* prioridades arquitectónicas

---

# ¿Por Qué Esto Importa?

La mayoría de arquitecturas malas NO se rompen por:

* frameworks equivocados,
* bases de datos equivocadas,
* o providers equivocados.

Se rompen por:

* constraints invisibles,
* supuestos irreales,
* mismatch operacional,
* o limitaciones organizacionales.

Esta propuesta mueve `funky assess` desde:

```txt
linting arquitectónico
```

hacia:

```txt
auditoría arquitectónica basada en constraints reales
```

---

# Evolución Propuesta para `funky assess`

## Comportamiento Actual

```txt
Ejecutar reglas locales
Si falla → generar review IA
Si pasa → no hacer auditoría profunda
```

---

## Comportamiento Propuesto

```txt
Ejecutar reglas locales
SIEMPRE generar architecture-review.md
```

El CLI pasa a ser:

* un validador heurístico rápido,
* * una capa de auditoría arquitectónica con IA.

Si las reglas locales fallan:

* la IA se enfoca agresivamente en esos riesgos.

Si las reglas pasan:

* la IA busca puntos ciegos, tradeoffs ocultos y supuestos peligrosos.

Esto formaliza:

```txt
CLI = filtro heurístico
IA = razonamiento arquitectónico
```

---

# Categorías de Constraints Propuestas

La nueva capa debería enfocarse en realidades de alto impacto.

## Realidad Operacional

* ¿Quién mantiene el sistema?
* ¿Existe DevOps/SRE?
* ¿Habrá on-call?
* ¿Es un proyecto solo-dev?

---

## Impacto de Fallos

* ¿Qué pasa si el sistema falla:

  * 5 minutos
  * 1 hora
  * 1 día?

---

## Disaster Recovery

* ¿Cuánta pérdida de datos es aceptable?
* ¿Frecuencia de backups?
* ¿Expectativas de recuperación?

---

## Compliance y Residencia

* ¿Datos gubernamentales/médicos/financieros?
* ¿Restricciones regionales?
* ¿Requisitos de auditoría?

---

## Realidad del Equipo

* ¿Senioridad del equipo?
* ¿Capacidad real de operar sistemas complejos?
* ¿Tolerancia a complejidad operacional?

---

## Prioridades Arquitectónicas

¿Qué se prioriza realmente?

* velocidad de entrega
* bajo costo
* confiabilidad
* escalabilidad
* simplicidad
* compliance

---

# Principio de Diseño Importante

El objetivo NO es:

```txt
más templates
```

El objetivo es:

```txt
mejor extracción de constraints arquitectónicos
con carga cognitiva progresiva
```

Debemos evitar:

* formularios gigantes,
* burocracia enterprise innecesaria,
* exceso de campos obligatorios.

La idea es:

* profundizar contexto únicamente cuando el proyecto lo necesita.

---

# Valor Estratégico a Futuro

Esta evolución desbloquea naturalmente futuras funcionalidades.

Toda esta información estructurada puede alimentar:

* Project Cost & Pricing Estimator
* recomendaciones automáticas de infraestructura
* scoring de riesgo
* generación de ADRs
* debates arquitectónicos con IA
* detección automática de red flags
* análisis de complejidad del proyecto
* inteligencia contextual para onboarding

Esto convierte el sistema de assessment en:

```txt
una capa reutilizable de inteligencia arquitectónica
```

en lugar de un cuestionario estático.

---

# Próximo Paso Propuesto

Antes de expandir agresivamente el template actual, deberíamos discutir:

1. Si los constraints arquitectónicos merecen su propia capa dedicada.
2. Cuánta carga cognitiva queremos durante el onboarding.
3. Qué campos deberían ser:

   * obligatorios,
   * opcionales,
   * condicionales,
   * o dependientes del perfil del proyecto.
4. Si `funky assess` debería evolucionar hacia un pipeline progresivo de revisión arquitectónica, en lugar de ser una validación estática única.
